# R6-1 S3 payload 축소 - 오프라인 토큰 판정 (issue #387, 상위 #386)

**벤치 G3 추정 토큰 증가는 +0.16%다(런 5 +40.6%, 문턱 +5%).**
**벤치 dev 질의 부착률은 2/40 = 5.0%, dev 상태 질의 부착률은 94/94 = 100%다.**
**대가: dev 표 키는 C1의 80~94%(t별 자카드 0.80~0.94, 빠진 키 7~8), 원래 증상 표 키는 126 -> 93이다.**
**질의마다 표가 달라져, 서로 다른 표 텍스트를 이어 붙이는 d-llm 입력은 텍스트 기준 최대 18.6%로 커진다(C1 2.2%).**

지출 0, 사본 0, LLM 호출 0. 런 5 저장물에 새 기본 손잡이를 게이트웨이 공개 함수로 그대로 적용했다(`bench/r6_payload.py`).
종단 d-llm·G3 측정은 R6-2(#388) 몫이다.

## 1. 바꾼 것 (`gateway/item_open_table.py`, 플래그 `HC_ITEM_OPEN_TABLE` 기본 꺼짐 유지)

| 항목 | 런 5(C1) | R6-1 기본값 |
|---|---|---|
| payload 모양 | `{t, fmt, rows, truncated, text}`(`rows` = 키·상태·날짜) | `{t, fmt, keys, truncated, text}`(`keys` = 열린 키만, 상태·날짜와 `recent_done_days` > 0일 때의 최근 끝남 키는 `text`만) |
| `attach` | `always` | `status_query` |
| `status_terms` | 12개(`STATUS_TERMS_V1`로 남김) | 35개(할 일·남은·진행·끝·미완·상태·목록 계열, 영어 `open` 뺌) |
| `scope` | `request_project`(태그 없으면 뱅크 전체) | `request_or_result_project`(요청 project, 없으면 결과 행 키의 repo, 결과에 키가 없으면 붙이지 않음) |
| 감사 줄 | `attached` / `not-attached` | 같은 사유 + `not_attached`(`no-status-term` / `no-result-keys`, 요소 여럿이면 사유별 개수), 붙이면 `scope_from`(`request` / `result` / `all`별 요소 수) |

- `build_table` 반환 모양(`rows` 포함)은 그대로다(런 5 하네스가 쓴다). payload에 붙일 때만 `payload_table`로 바꾼다.
- 기본 손잡이 정규 sha256: 런 5 `f7fcf626...` -> **`0ca334da8e68e695b1248da30df7616e7818c97ead3041e4d8cb9026c01883b7`**.
- `bench/r5_tune.py` C1 손잡이(attach·scope를 명시)는 표 내용이 같고 정규 sha만 `dfcc684d75bd...`로 바뀐다(기본 어휘 반영). C1에 `STATUS_TERMS_V1`을 넣으면 `f7fcf626...`가 그대로 나온다.
- 키 상태 계산(`role_states`)과 S4 저장소 계약(스키마 v1)은 바꾸지 않았다.

### 어휘를 고른 근거

- 판별은 부분 문자열 일치(대소문자 무시)다. 런 5 어휘의 `open`은 벤치 dev 질의 4개에서 `open`으로 시작하는 도구 이름에 걸렸다. 맨 `진행`(2개)·`완료`(3개)도 일반 질의에 걸려, `진행 중`·`진행 상태`·`진행 상황`처럼 마디로 좁혔고 `완료`는 넣지 않았다.
- dev 상태 질의는 지시문 없이 문안만으로도 94/94가 새 기본 어휘에 걸린다(질의 가족별 적중 낱말은 리포 밖 측정 기록에만 둔다).
- 새 어휘가 벤치에서 걸린 낱말: `미완` 1, `진행 상황` 1, `현황` 1(셋 다 상태를 묻는 질의). 그중 1개는 결과에 키가 없어 붙지 않았다.

## 2. 벤치 (런 5 G3 run `r5d-g3-r1` cand 40질의, 응답 payload 기준)

| 항목 | 값 |
|---|---|

| 부착 | **2 / 40 = 5.0%** (사유: `no-status-term` 37, `no-result-keys` 1, 결과 범위 2) |
| 붙은 질의 표 키 수 | 7, 17 |
| 붙은 질의 추가 토큰 cl100k / o200k | 245, 367 / 198, 300 |
| G3 추정(추가 o200k 합 / base 응답 토큰 합 305,247) | **+0.16%** (498토큰) |
| 보정: 런 5 표 객체로 같은 셈 | +40.59% (compare 기록 +40.58%, 질의당 p50 3,475 vs 기록 3,474) |

- 추가 토큰 = `"gateway_item_open_table":` + 표 객체 압축 JSON(`recall_prune._dumps`). G3 비교기(`arm_compare`)는 질의마다 라운드 중앙값을 낸 뒤 질의 합을 쓰므로 라운드를 곱하지 않는다.
- 결과 행은 저장된 cand 응답(뒤 패스 prune 뒤)이다. 게이트웨이 S3는 prune 앞의 행을 본다. 키 추출 대상 행이 조금 다를 수 있다(한계).
- 속도·p95는 오프라인으로 잴 수 없다. R6-2 G3에서 잰다.

- 부착률 100%(목표 충족). 지시문의 상태 낱말 없이 문안만으로도 100%다.
- 사유는 94질의 모두 결과 범위다(태그 없는 질의, 결과에 키가 있음).

- 빠진 키 7~8은 결과에 나오지 않은 repo의 열린 키다. #365 3절 "질의 범위 프로젝트로 좁힌 열린 키"(33/35/85/100/103/101)와 거의 같은 크기다. R6-2 dev R_bank에서 이 키들이 양성이면 회수가 줄 수 있다.
- 분모 = #365 `prep` 기록값(필터 뒤 d-llm 입력 토큰, `r5-c-tune.md` 3절). 질의당 응답 하나에 실리는 양(payload)은 C1의 약 절반이다.
- **이은 표 텍스트**: 질의마다 결과 repo가 달라 t마다 표 텍스트가 5~11개로 갈린다. 런 5 하네스처럼 서로 다른 텍스트를 모두 이어 d-llm 입력에 붙이면 겹친 키가 반복돼 텍스트 기준 최대 18.6%다(#365 선택 규칙 상한 10%). R6-2가 d-llm 입력을 조립하는 방식(이어 붙이기, 키 합집합 표 1개 등)을 정해야 한다.

## 6. 한계

- 벤치 결과 행은 prune 뒤 저장본이다(2절). 응답 토큰·속도는 R6-2 G3가 실측한다.
- 결과 키가 있지만 그 repo에 열린 키가 없으면 빈 표(머리만)가 붙는다(감사 줄 `attached`, 표 줄 0). 이번 입력에서는 그런 질의가 없었다. R6-2가 빈도를 잰다.
- 상태 어휘 판별은 부분 문자열이다. 벤치 dev 분할 40질의로만 골랐으므로, 넓은 낱말(상태·목록·status 등)이 운영 일반 질의에 걸리는 비율은 다를 수 있다. 운영 창 연막에서 부착 비율을 확인할 항목이다.
- 기본 어휘 교체로 `bench/r5_tune.py` C4(attach status_query, 어휘 미지정)를 다시 계산하면 부착 판정과 정규 sha가 런 5와 달라진다. 런 5는 마감이라 기록값을 유지한다.
- 표를 붙일 요소가 있었지만 응답 표면이 `results` 목록을 가진 JSON 객체가 아니어서 붙이지 못한 경우, 감사 줄은 `not-attached`만 남고 `not_attached` 하위 사유가 없다.
